# 信息流仓库（FeedRepository）：数据是怎么一步步拿到的

> 面向对象：刚接触本项目、想搞清楚「点开一个 Tab，文章列表是怎么来的」的初级程序员。
> 涉及文件：`lib/providers/core_providers.dart`、`lib/services/feed_repository.dart`、
> `lib/services/generic_feed_parser.dart`、`lib/services/keyword_filter_engine.dart`、
> `lib/services/translator_service.dart`。

---

## 一、一句话总览

`FeedRepository`（信息流仓库）是 **UI 层获取数据唯一要打交道的入口**。

它把三个「零件」组合在一起，按固定顺序干完一件完整的事：

| 零件                  | 是什么              | 在流程里干嘛                              |
| --------------------- | ------------------- | ----------------------------------------- |
| **Dio**               | 一个网络请求库      | 负责「发请求、把网页/接口的 JSON 拿回来」 |
| **AppDatabase**       | 本地数据库（drift） | 负责「读出用户设的屏蔽词」                |
| **TranslatorService** | 翻译服务            | 负责「把外文标题翻译成中文」              |

三者配合，最终交给 UI 一份 **已经解析好、过滤掉屏蔽词、可能还翻译过** 的干净文章列表。

> 💡 为什么叫「仓库（Repository）」？因为 UI 不需要知道 Dio、JSONPath、屏蔽词这些脏活，
> 它只要喊一句「给我某某数据源的第 1 页」，仓库内部把一切办妥。这就是经典的 **Repository 模式**。

## 二、整体流程图

```mermaid
flowchart TD
    A[UI: 我要数据源X的第1页] --> B[FeedRepository.fetchFeed]
    B --> C[1. 拼 URL<br/>替换 {page} {pageSize}]
    C --> D[2. Dio 发网络请求<br/>GET/POST]
    D -->|网络出错| Z1[抛 FeedFetchException]
    D -->|拿到响应| E[3. 响应体统一转成 Map]
    E --> F[4. GenericFeedParser<br/>按配置解析成 List&lt;FeedArticle&gt;]
    F -->|路径写错| Z2[抛 FeedParseException]
    F --> G[5. 从数据库读屏蔽词<br/>KeywordFilterEngine 过滤]
    G --> H{summaryPath 是<br/>翻译标记吗?}
    H -->|否| I[直接返回文章列表]
    H -->|是| J[6. TranslatorService<br/>批量翻译后写回]
    J --> I
    I --> K[UI 拿到干净列表去渲染]
```

如果不支持上面的图，用文字版也一样：

```
UI 调用
  → 拼 URL
  → Dio 发请求
  → 响应转 Map
  → 通用解析（JSON → 文章列表）
  → 屏蔽词过滤（读数据库）
  → 如需翻译，调翻译服务
  → 返回列表给 UI
```

## 三、逐步拆解（每一步都发生了什么）

下面是 `feed_repository.dart` 里 `fetchFeed()` 方法的核心流程，建议边看代码边读。

### 第 1 步：拼 URL（处理分页）

```dart
final url = config.apiUrl
    .replaceAll('{page}', page.toString())
    .replaceAll('{pageSize}', pageSize.toString());
```

用户配置数据源时会填一个地址，比如 `https://api.xxx.com/list?p={page}`。
请求第 2 页时，这里的 `{page}` 会被替换成 `2`。**这一步只是字符串替换，还没真正联网。**

### 第 2 步：Dio 发网络请求

```dart
response = await _dio.request(
  url,
  options: Options(method: config.method), // GET 还是 POST 由配置决定
  queryParameters: config.queryParams,
);
```

Dio 出场，真正去网上把数据拉回来。**这是整个流程里唯一会「卡住等待网络」的地方**（`await`）。

如果网络本身出问题（断网、超时、404），这里会单独抛 `FeedFetchException`，让 UI 能区分「网络挂了」和「配置写错了」这两种不同的错误文案。

### 第 3 步：把响应体统一成 Map

Dio 返回的可能是已经解析好的对象，也可能是字符串。代码做了兼容处理，最终统一成
`Map<String, dynamic>`（也就是「一个 JSON 对象」），方便后面按路径取值。

如果响应根本不是 JSON（比如服务器返回了一段 HTML 报错页），这里会抛 `FeedParseException`。

### 第 4 步：通用解析（JSON → 文章列表）

```dart
parsed = GenericFeedParser.parse(json, config);
```

这是整个设计里**最巧妙**的一步。解析器本身 **不认识任何具体 API**，它完全照着 `config`（用户填的字段映射规则）办事：

- `config.fieldMapping.listPath` 告诉它：文章数组在哪个路径下（比如 `data.list`）
- `config.fieldMapping.titlePath` 告诉它：每条里的标题字段叫什么
- 同理还有 `summaryPath`、`thumbPath`、`authorPath` 等

举例，假设 API 返回：

```json
{
  "data": {
    "list": [{ "post_title": "今天天气真好", "pic": "https://.../a.jpg" }]
  }
}
```

只要用户在配置里写：

```
listPath   = data.list
titlePath  = post_title
thumbPath  = pic
```

解析器就能正确产出 `FeedArticle` 列表。**这意味着：新增一个数据源，只要填配置，完全不用改这层代码。** 这就是「JSONPath 声明式」的含义。

> ⚠️ 容错约定（看代码能学到）：
>
> - 定位不到数组 → 直接报错（不静默返回空，避免你以为没数据其实是路径写错）
> - 单条标题为空 → 当作脏数据丢掉（不显示空白卡片）

### 第 5 步：屏蔽词过滤（读数据库）

```dart
final keywords = await _db.getActiveBlockedKeywords(); // 从本地数据库读「还生效」的屏蔽词
var articles = KeywordFilterEngine(keywords).filter(parsed);
```

用户之前在「屏蔽词」页面加过一些词（比如「广告」「剧透」）。这些词存在本地数据库里。
`KeywordFilterEngine` 的逻辑很简单：**文章的「标题+摘要」里只要包含任意一个屏蔽词，就丢弃。**

注意 `getActiveBlockedKeywords()` 只取「还没过期的」词——有些屏蔽词设了有效期，过期自动失效。

> 为什么过滤放在仓库里、而不是放在 UI？因为这样无论怎么分页、怎么去重，都绕不过过滤，
> 保证用户永远看不到想屏蔽的内容。

### 第 6 步：翻译（可选，按需触发）

```dart
final marker = TranslatorService.parseMarker(config.fieldMapping?.summaryPath);
if (marker != null && articles.isNotEmpty) {
  articles = await _translateField(articles, ...);
}
```

只有当用户把某个路径字段配置成 **翻译标记** 时才触发。例如把 `summaryPath` 写成
`title.tttttranslate`，意思是「把每条文章的 `title` 翻译成中文，译文放进 `summary`」。

机制：

1. `parseMarker` 识别这个特殊写法，提取出「要翻译的源字段=title、目标语言=zh-CN」
2. 收集所有文章的标题原文
3. 一次性交给 `TranslatorService.translate()` 批量翻译（只发一次网络请求）
4. 把译文按原顺序写回文章的 `summary` 字段

**所以你会看到：标题保留原文，第二行摘要显示译文。**

> 💡 顺序很重要：翻译放在**过滤之后**。因为被屏蔽的文章反正不显示，没必要浪费一次翻译请求。
> 这正是代码里 `_translateField` 在 `KeywordFilterEngine.filter` 之后才执行的原因。

## 四、数据长什么样（形态一路变化）

| 阶段      | 数据类型               | 长啥样                             |
| --------- | ---------------------- | ---------------------------------- |
| 第 2 步后 | `Response`             | 原始 HTTP 响应（JSON 字符串/对象） |
| 第 3 步后 | `Map<String, dynamic>` | 一个 JSON 对象                     |
| 第 4 步后 | `List<FeedArticle>`    | 一堆文章对象（字段已映射好）       |
| 第 5 步后 | `List<FeedArticle>`    | 少了几条被屏蔽的                   |
| 第 6 步后 | `List<FeedArticle>`    | 摘要被译文替换（如果开了翻译）     |
| 最终      | `List<FeedArticle>`    | UI 拿去渲染列表                    |

`FeedArticle` 是项目里统一的「文章」数据结构，包含 `id / title / summary / thumbUrl / author / publishTime / detailUrl` 等字段。
无论后端 API 长什么样，经过第 4 步后都变成同一种结构，UI 只用认这一种结构即可。

## 五、三个零件在 core_providers.dart 里怎么接起来的

`core_providers.dart` 是「组装工厂」。关键几行（语义等价，行号可能随改动变动）：

```dart
// 全局 Dio 实例
final dioProvider = Provider<Dio>((ref) => DioClient.create());

// 翻译服务（可以给翻译单独挂本机代理，不影响其它请求）
final translatorServiceProvider = Provider<TranslatorService>(
  (ref) => TranslatorService(ref.watch(dioProvider), proxyUrl: ...),
);

// 信息流仓库：把三个零件一次性注入
final feedRepositoryProvider = Provider<FeedRepository>(
  (ref) => FeedRepository(
    ref.watch(dioProvider),              // 零件1：网络
    ref.watch(appDatabaseProvider),      // 零件2：数据库（屏蔽词）
    ref.watch(translatorServiceProvider),// 零件3：翻译
  ),
);
```

`ref.watch(...)` 是 Riverpod 的依赖注入：仓库说「我需要 dio、数据库、翻译服务」，
框架自动把对应的实例递过来。**仓库自己不 new 这些零件，零件由上层统一提供**，方便测试和替换。

UI 层只要 `ref.watch(feedRepositoryProvider).fetchFeed(config)` 就能拿到数据，对内部三个零件一无所知。

## 六、异常怎么分（初级必看）

代码故意把两类错误分开抛，方便 UI 给出不同提示：

| 异常                 | 触发场景                                 | UI 该提示                        |
| -------------------- | ---------------------------------------- | -------------------------------- |
| `FeedFetchException` | 第 2 步网络层出错（断网/超时/404）       | 「网络异常，请检查连接」         |
| `FeedParseException` | 第 3/4 步：响应不是 JSON，或字段路径写错 | 「该数据源配置有误，请检查路径」 |

**练习**：如果你加了一个新数据源，列表一直空，先看日志里抛的是哪个异常——
`FeedParseException` 八成是 `listPath`/`titlePath` 写错了；`FeedFetchException` 则是地址或网络问题。

## 七、小结（记住这 3 点就够了）

1. **顺序是死的**：请求 → 解析 → 过滤 → （按需）翻译。解析必须在过滤前，翻译必须在过滤后。
2. **配置驱动**：新增数据源基本只填 `DataSourceConfig`（尤其是 `fieldMapping`），不用改 `FeedRepository` 代码。
3. **仓库对外只给干净数据**：UI 拿到的 `List<FeedArticle>` 已经是解析好、过滤过、可能翻译过的，可以直接渲染。

> 本文档基于撰写时的代码结构，行号/字段名若日后有调整，以代码为准，但「请求→解析→过滤→翻译」的主干顺序不会变。
